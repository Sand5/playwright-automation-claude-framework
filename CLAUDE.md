# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status

Playwright Test project (TypeScript, CommonJS) testing the Demoblaze demo store (`https://demoblaze.com`; `baseURL` comes from `BASE_URL` in `env/.env.qa`, and the config throws if it is unset). Tests are BDD scenarios run with `playwright-bdd`: Gherkin in `features/` (`homepage.feature`, `login.feature`), step definitions in `step-definitions/`, built on a page object model. There are no hand-written specs. No `webServer` is configured.

## Commands

Prefer the npm scripts; use `npx` for anything else. **Every test script runs `bddgen` first**, which regenerates the specs in `.features-gen/` from the `.feature` files. Plain `npx playwright test` does not, so run `npm run bddgen` first after editing a feature or step, or it runs stale specs.

- Chromium headed: `npm run test:chrome:headed`
- Chromium headless: `npm run test:chrome:headless`
- WebKit headless: `npm run test:webkit:headless`
- Login scenarios (`@login`, Chromium): `npm run test:login` / `npm run test:login:headed`
- Smoke tests (`@smoke`): `npm run test:smoke` (Chromium) / `npm run test:smoke:all` (all browsers)
- Any tag (Chromium): `npm run test:tag -- @login`
- Run all tests (all 3 browsers): `npm run test:all`
- Generate specs only: `npm run bddgen`
- Single feature file (Chromium): `npm run test:feature -- homepage.feature`
- Single scenario by title: `npm run bddgen && npx playwright test -g "scenario title"`
- Ordered log output (no interleaving between tests): add `--workers=1`
- UI mode / debug / codegen (run `npm run bddgen` first): `npx playwright test --ui`, `npx playwright test --debug`, `npx playwright codegen <url>`
- Open last Playwright HTML report: `npx playwright show-report`
- Cucumber HTML report: run tests, then `npm run report:cucumber` and open `cucumber-report/html/index.html`
- Type-check: `npm run typecheck`
- Lint: `npm run lint` / `npm run lint:fix`
- Format check: `npm run format:check`; write with `npx prettier --write <paths>`
- Lint feature files: `npm run lint:features` (gherkin-lint, config in `.gherkin-lintrc`: 2-space indentation, kebab-case file names, no duplicate or unnamed scenarios)
- Full QA gate (typecheck + lint + feature lint + format check): `npm run qa:check` — run before finishing any change
- (Re)install browsers: `npx playwright install`

## Project structure

- `features/` — Gherkin `*.feature` files, one per area. Describe behaviour in plain steps; no selectors and no expected values (those come from `test-data/` via the steps). Tag scenarios, e.g. `@smoke @login`, so they can be run with `--grep`. Use `Background` for shared setup and `Scenario Outline` + `Examples` for repeated cases.
- `step-definitions/` — step code. `fixtures.ts` extends the `playwright-bdd` `test` with the page objects (`homePage`, `loginPage`) and an `alert` recorder, and exports `Given`/`When`/`Then`/`Before`/`After` (import them from there, not from `playwright-bdd`). `hooks.ts` logs the scenario title in `Before` and logs out in `After` for `@login`. `home.steps.ts` / `login.steps.ts` hold the steps. **Assertions live in steps, not in page objects.** Steps share state through fixtures, not local variables.
- `.features-gen/` — specs generated by `bddgen` from the features. Git-ignored; never edit.
- `pages/` — page objects, named `<name>.page.ts` (lowercase file, PascalCase class). `base.page.ts` has the abstract `BasePage` (holds `page`, provides `navigate(url)` which logs). Page objects extend it, expose locators as `readonly` properties, and log their actions with the logger. Use relative paths in `navigate()`/`goto()`; the host comes from `baseURL`.
- `test-data/` — expected values (titles, headings, product lists) as `as const` objects, e.g. `home.data.ts`, `login-data.ts` (credentials and expected welcome text). Don't hardcode expected strings in feature files or steps.
- `logger/logger.ts` — shared winston logger (coloured console output, Europe/London timestamps). Level comes from `LOG_LEVEL`, loaded via `config/load-env.ts` from `env/.env.<TEST_ENV>` (default `qa`) (paths resolve from that file, not the working directory; Playwright itself still needs to run from the project root to find its config).

## Configuration notes

- Reporting: `playwright.config.ts` runs the Playwright `html` reporter plus playwright-bdd's Cucumber `json` reporter (`cucumber-report/cucumber.json`). `scripts/generate-cucumber-report.ts` (run with `tsx` via `npm run report:cucumber`) turns that JSON into a `multiple-cucumber-html-reporter` report in `cucumber-report/html/`. That package is ESM-only, so the script loads it with a dynamic `import()`. `cucumber-report/` is git-ignored and ESLint-ignored. Each test run overwrites the JSON, so generate the report straight after the run you want.

- `playwright.config.ts` defines three projects: chromium, firefox, webkit (desktop devices). `fullyParallel` is on; on CI (`CI` env var) it uses 1 worker, 2 retries, and fails on stray `test.only`. The `chromium` project is Playwright's bundled Chromium, not branded Chrome.
- Reporter is `html`; output goes to `playwright-report/` and `test-results/` (both git-ignored).
- `tsconfig.json` uses `module`/`moduleResolution: nodenext` (not `node10`, which is deprecated in TS 6+) and explicitly loads `types: ["node"]`. Its `include` covers `playwright.config.ts`, `config/`, `step-definitions/`, `pages/`, `logger/` and `test-data/` — add any new source directory there or the editor will lose type info for it.
- Prettier is configured in `.prettierrc` (`singleQuote: true`, `semi: true`). `format:check` covers `step-definitions/`, `pages/`, `logger/`, `test-data/`, `config/` and `playwright.config.ts`.
- ESLint is configured in `eslint.config.mjs` (flat config: typescript-eslint type-checked rules + `eslint-plugin-playwright` for `step-definitions/`; `.features-gen/` is ignored). Notable rules: no floating promises, no `console` (use the logger), no `waitForTimeout`/`force`, and no `expect` in `pages/`. `no-standalone-expect` is off for steps because they are not inside a `test()` block. ESLint only covers `.ts` files; `.feature` files are linted by `gherkin-lint` (`npm run lint:features`) but not auto-formatted.
- Environments: `TEST_ENV` (default `qa`) selects `env/.env.<TEST_ENV>`; the loader throws if that file is missing. To add staging, create `env/.env.staging` with its own `BASE_URL` and run `TEST_ENV=staging npx playwright test`. Real environment variables (e.g. `BASE_URL` set in the shell or CI) override the files.
- Credentials: `test-data/login-data.ts` reads `TEST_USERNAME`/`TEST_PASSWORD` from the environment. `config/load-env.ts` (imported by `playwright.config.ts`, `logger/logger.ts` and `login-data.ts`; the only place that calls dotenv — import it for its side effect in any new file that reads env vars) loads `env/.env.secrets` (git-ignored; template in `env/.env.secrets.example`) then `env/.env.qa` (committed, non-secret only). In CI they come from GitHub secrets. The `test`/`test` fallback is a **demo-only** default for Demoblaze's public account — never add default credentials for a real environment, and never put secrets in `env/.env.qa`.
- CI is `.github/workflows/ci.yml`: a `qa` job (`npm run qa:check`) gates an `e2e` job that runs each browser project in a matrix and uploads the Playwright HTML report and the Cucumber HTML report (`cucumber-report-<browser>` artifact). Triggers: push to `main`, pull requests, manual dispatch.
- Project skill `verify-test-outcomes` (`.claude/skills/verify-test-outcomes/SKILL.md`, invoke with `/verify-test-outcomes` or `npm run review:tests`, which runs `claude -p "/verify-test-outcomes"`; keep it out of `qa:check` and CI) reviews the `.feature` scenarios and the step definitions behind them to confirm each scenario asserts a meaningful outcome, not just presence. Use it when writing or changing features or steps and before pushing; it reports first and only edits if asked. Lint cannot do this check, since `expect-expect` does not apply to steps.
- The tests must run without Claude Code or MCP (see `CLAUDE_SETUP.md`).
